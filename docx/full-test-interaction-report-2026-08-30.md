## 5. 发现与处理

### 5.1 富文本工具栏专项测试误报

首次补跑 `check-rich-toolbar-layout.js` 时失败，报告“常驻工具栏不可见”。诊断确认产品行为正常，失败原因是测试仍假设“新增思维节点后需要双击进入编辑”。当前行为是新增节点即进入编辑，旧脚本再次双击会退出编辑，因此产生误报。

处理：

- 先读取当前 `editingId`，仅在尚未进入目标节点编辑态时双击。
- 补充视图缩放和偏移换算，避免使用未经转换的画布坐标。
- 选区覆盖整个富文本编辑器，避免依赖首个子节点结构。
- 单行布局改为比较直接子控件的垂直中心，不再把不同高度色块或嵌套弹层误判为换行。
- 新增 `Escape` 退出恢复检查和 3 次快速进入/退出检查。

修正后结果：常驻工具栏可见且 `flex-wrap: nowrap`；所有直接子控件垂直中心一致；选区工具栏可见且两行位置分别为 13 px 和 47 px；退出与 3 次快速循环后 `editingId` 清空，两个工具栏均隐藏。

## 9. 映射控制与画布交互架构升级追加报告

### 9.1 本轮结论

- 实施日期：2026-08-30（Asia/Shanghai）。
- Git 起始基线：`main` / `a21547e`，开始时工作区干净，本地分支比 `origin/main` 领先 21 个提交。
- 实施结论：通过。映射跟随延迟、画布缩放闪烁、低缩放背景空白、overlay 跳闪和长输入顶开画布按同一套“高频交互协调与布局边界”体系处理。
- 最终统一测试：`npm test` 退出码 0，明确输出 `[test] all checks passed`。
- 报告口径：仅记录实际执行结果。未制作 Windows 安装包，也未在真实第三方窗口上进行 Win32 原生嵌入的人工拖拽体验，因此不将这两项记为通过。

### 9.2 根因归纳

这些现象属于同一问题域，但不是单个函数造成：

1. 高频输入缺少统一背压。拖拽、缩放和滚轮事件到达速度高于跨进程边界同步、持久化及 DOM overlay 更新速度，旧请求会排队并在新状态之后到达。
2. 相机状态存在多个提交节奏。滚轮事件逐次修改正式视图并持久化，渲染、命中测试和 overlay 可能在同一时刻读取不同版本的相机。
3. Canvas backing store 改尺寸会立即清空。旧逻辑把重绘留到下一帧，期间会暴露透明或空白帧。
4. Canvas 与 DOM overlay 同时承担交互帧。两套渲染层在缩放时分别测量和更新，造成内容追赶、跳闪以及节点销毁后重建。
5. LOD 只有单阈值。缩放在边界附近往返时会频繁切换 Canvas/DOM 表现。
6. 输入区缺少严格的内部滚动和布局隔离。长内容高度会参与右面板布局竞争，进而挤压画布区域。

### 9.3 分批实施内容

第一批，映射边界协调：

- 增加 latest-only 异步提交协调器：提交保持单飞，在途期间只保留最新值，相同边界去重，并支持会话重置、错误恢复及等待空闲。
- 映射同步增加会话标识、递增 revision、目标和来源校验；WebContentsView 与 Win32 接收端拒绝旧会话、旧 revision 和错误目标。
- 面板移动移除重复动画帧；面板缩放按动画帧聚合，并在结束时强制提交最后尺寸。
- 高频拖拽保持无等待；用户主动切换适配模式时等待提交队列完成，并传播最终错误后再显示成功状态。

第二批，Canvas 相机与交互状态机：

- 连续滚轮基于 pending view 聚合，每个动画帧最多提交一次正式相机；160 ms 无新事件后只持久化最终视图。
- 指针命中测试前刷新 pending view，避免点击读取旧相机；缩放按钮、minimap、动画导航和卸载统一结束旧滚轮会话。
- 提交结束会清理滚轮原因和旧定时器，避免按钮缩放后再发生一次过期提交。
- 渲染器显式记录 `viewport-interaction` 与 `steady` 模式，便于验证进入、连续操作和恢复。

第三批，渲染层与 LOD：

- 视口缩放和平移期间由 Canvas 接管文本绘制。
- 富文本、数学和代码 overlay 在交互期间只隐藏宿主，不销毁已有 DOM 节点；恢复帧切回 DOM，保留节点身份和内容。
- LOD 使用 15% 进入、17% 退出的滞回区间，减少阈值附近反复切换。
- Canvas backing store 尺寸变化后同帧强制重绘背景和内容，不暴露 resize 后的透明帧。

第四批，输入与布局边界：

- 右侧面板明确划分 header、内容区和 composer 三行，内容区可收缩。
- composer 增加尺寸约束与布局/绘制隔离。
- 输入框最大高度按面板高度动态计算，上限 220 px；超出后仅在输入框内部纵向滚动，清空后恢复默认高度。

### 9.4 状态机与恢复链验证

映射同步：

- 进入：建立新 session，revision 从 1 递增。
- 连续操作：同一时间最多一个原生提交在途，等待区仅保留最新边界。
- 退出：停止映射时重置 session 并丢弃旧等待值。
- 快速重入：新 session 的接收端校验阻止旧异步结果覆盖新目标。
- 失败恢复：一次提交失败会报告错误，协调器仍可继续处理下一次提交并回到 idle。

画布视口：

- 进入：滚轮或指针平移激活 `viewport-interaction`，Canvas 接管文本，DOM overlay 隐藏但节点保留。
- 连续操作：24 次同步滚轮事件在当前调用栈内未修改正式 scale；下一动画帧统一提交。
- 退出：无新滚轮 220 ms 后实测恢复 `steady`，三类 overlay 可见且节点身份未变化。
- 快速切换：滚轮后立即使用缩放按钮、minimap 或导航时，旧定时器与原因被统一清理。
- 卸载：最终 pending view 持久化，动画帧、计时器、交互门和 hydration 暂停状态均清理。

LOD 与布局：

- 初始低缩放时不创建不必要的 overlay 节点。
- 从正常缩放进入低缩放时保留既有节点；17% 恢复后内容、无骨架状态和零 padding 正常。
- 再次降到 15% 区间并再次恢复后，节点与内容仍正常。
- 输入 4000 字以上内容时画布 frame 宽、高和左边界保持不变，输入框出现内部滚动；清空后输入高度回到 40 px 以内，画布布局恢复。

### 9.6 测试过程中的诊断

- 新增滚轮检查首次只等待一个动画帧，读取到相机已提交但 render stats 尚未更新的边界时序；改为等待两个动画帧后稳定验证相机和渲染模式。
- LOD 首次恢复用例曾把元素放在左上角，却连续调用以视口中心为焦点的放大，元素实际移出可视区，因此按裁剪规则没有创建 overlay。将相机初始偏移改为保持被测元素位于视口内后，首次恢复、再次隐藏和再次恢复均通过。该问题属于测试几何前提，不是产品缺陷。
- 提交前审计发现滚轮最终提交后原因未清空、缩放按钮可能留下旧持久化定时器；已统一滚轮会话出口并重新完成全量回归。
- 提交前审计发现适配模式切换的 `await` 在队列化后只等待到序号返回；已增加可选等待空闲和错误传播，再次完成协调器、生成产物、打包静态检查和最终 `npm test`。
